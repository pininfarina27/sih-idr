1. Official Problem Statement (reference — keep this context, don't lose it)
Core problem: Phone-based navigation (GPS/GNSS) fails in tunnels, multi-level parking, dense forests/urban canyons, or under jamming. Most Indian vehicles (trucks, older cars, two-wheelers) have no factory INS and no OBD-II speed feed — only a dashboard-mounted smartphone. Its consumer-grade MEMS IMU (accelerometer + gyroscope) drifts exponentially within seconds if you just integrate it naively. The ask is an AI/ML-enhanced dead-reckoning + GNSS fusion engine that keeps lane-level position accuracy through a GNSS blackout and hands back to GNSS smoothly when it returns.
Expected solution components (all six, per the official brief):
In-vehicle alignment/calibration engine — auto-detect phone pitch/roll/yaw vs. vehicle heading, regardless of mount.
AI speed & vibration filter — filters engine/road noise and pothole shocks, estimates forward velocity from IMU alone.
Map-matching + kinematic constraints — snaps drifting position back onto the road graph (e.g. via Non-Holonomic Constraints — a car can't slide sideways or fly).
GNSS+INS fusion engine — AI-based sensor fusion combining GNSS and IMU, reducing drift.
Seamless GNSS-deficit handler — instant, sub-second mode switching between GNSS-aided and pure dead reckoning.
Real-time navigation UI — smooth vehicle icon, no visible jumps.
Performance benchmarks (official, must be visibly addressed):
Dead reckoning drift < 10% of distance travelled during blackout — e.g. <5 m drift over 50 m in <1 min, OR <100 m drift over 1 km at 60 km/h (tunnel-scale).
GNSS+INS fusion update rate: 10 Hz on smartphone; higher (~200 Hz) on FOG-IMU edge hardware (this edge part is out of scope for this round — see Section 3).
Teams must submit preliminary AI models + a position plot inferenced from a subset of IO-VNBD as part of screening — this is a hard requirement even at this stage, not optional polish.
2. Full solution vs. prototype — the decision, and why
The full SIH ask spans: a production mobile app, a separate edge-deployable engine for external/FOG-grade IMUs, models trained on the full 40–58 hr dataset, live OBD-independent operation across real vehicles, and validation across two competition rounds with additional datasets provided only after screening.
None of that is gradeable or buildable in 20 hours, and it doesn't need to be for internal screening. Screening judges are checking three things: (1) do you understand the actual hard problem (drift, calibration, map-matching, fusion — not just "we'll use GPS"), (2) can you show it working, even on a slice of data, and (3) is there a believable path to the full solution later.
Decision: build one tight, working, demoable prototype that proves the core scientific claim — an AI/ML-enhanced fusion pipeline keeps drift within the benchmark thresholds where raw IMU dead-reckoning fails badly — wrapped in a polished, link-shareable web app with a live phone-sensor demo mode. Everything else goes in the README as "planned for the finale round," which is honest and expected at this stage.

4. Recommended architecture
No backend needed. This is a static, client-side web app (PWA) — simpler to build, trivially shareable as a link, and phone sensor APIs work fine from a deployed HTTPS static site.

Offline (Python, once, before the hackathon UI work):
  IO-VNBD subset → preprocessing → train small ML correction
  model → export results (plots + JSON tracks) → embed in web app
Component-by-component mapping to the official 6 requirements:
Tech stack:
Frontend: React + Vite (TypeScript), Leaflet.js (OSM tiles) for the map, Recharts or Chart.js for the drift plot.
Sensors: DeviceMotionEvent / DeviceOrientationEvent + Geolocation API — built into every phone browser, no app install, works the instant someone opens your link (requires HTTPS + a one-tap permission grant on iOS Safari — plan for that in the demo).
Map matching: turf.js against a small pre-downloaded OSM extract (Overpass API) for wherever you'll film the live demo, or against the IO-VNBD route for replay mode.
Offline ML training: Python (see Section 5), model kept small enough to either (a) reimplement its learned correction as simple weights/coefficients evaluated directly in TS, or (b) export via ONNX.js/TensorFlow.js if time allows. Prefer (a) for the 20-hour budget — it removes a whole class of in-browser-inference bugs and still is a genuine ML model, just deployed as its learned parameters rather than a runtime graph.
Hosting: Vercel or GitHub Pages — both give an instant public HTTPS URL, which you need anyway for phone sensor permissions to work at all.
5. Data & model plan
Pull a subset of IO-VNBD from the GitHub repo (smartphone-recorded segments are the most relevant — the dataset includes synchronized and unsynchronized vehicle + smartphone inertial/GPS data from drives in the UK, Nigeria, and France, sampled at 10 Hz).
Pick 2–4 driving segments, including at least one with varied dynamics (turns, hard braking) — you don't need the full 40+ hours.
Define an artificial "GNSS blackout window" inside a segment (e.g., mask out 30–60 seconds of GPS) — this is standard practice for benchmarking DR algorithms and is exactly what the official brief's benchmark examples describe.
Baseline (build first, on purpose): naive double-integration of raw accelerometer data through the blackout. It will drift badly — this demonstrates the problem and is a required contrast in your results plot.
Classical fusion layer: UKF/EKF with NHC, no ML yet — already a big improvement, and your fallback if the ML layer runs out of time.
AI/ML correction layer: a small model (gradient-boosted regressor or a tiny MLP — scikit-learn or PyTorch) trained on windowed IMU features to predict either (a) IMU bias correction or (b) zero-velocity/stationary probability (ZUPT), improving on the classical filter. This is your genuine "AI-ML" differentiator and satisfies the requirement without betting the whole prototype on a hard deep-learning problem finishing in time.
Compute drift % vs. distance travelled for each blackout segment, compare against the official thresholds, and generate the position plot (ground truth vs. raw DR vs. fused) — this exact artifact is explicitly required in the official screening brief, so treat it as non-negotiable, not a nice-to-have.
Export: model parameters/weights, the results plot images, and the track coordinates as JSON/GeoJSON for the web app's Replay Mode to consume directly (no need to run training or heavy inference in-browser).
